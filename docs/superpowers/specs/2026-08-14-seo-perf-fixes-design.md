# sever-18.ru — видимость в Яндексе, размер бандла, Cloudflare

Дата: 2026-08-14

## Проблема

Три независимые находки по сайту sever-18.ru:

1. **Сайт невидим для Яндекса.** Приложение — чистый Vite/React SPA. Сырой HTML отдаёт
   пустой `<div id="root"></div>`, весь текст (услуги, цены, адрес) появляется только
   после выполнения JS в браузере. Googlebot с этим справляется, Яндекс — заметно хуже,
   а для копи-центра в Раменском Яндекс — основной источник поискового трафика.
2. **Главный JS-файл сайта — 850 КБ** (до сжатия), грузится всегда, даже для гостя,
   который просто открыл страницу с ценами. Dashboard и AdminPanel уже вынесены в
   отдельные чанки и не входят в эту цифру.
3. **Cloudflare не проксирует трафик.** `curl -I https://sever-18.ru/` отдаёт
   `Server: nginx-reuseport` напрямую, никаких признаков Cloudflare (CF-RAY и т.п.) в
   ответе нет — прокси выключен или не настроен.

## Цели

- Гостевая посадочная страница (`LandingPage.tsx`) отдаёт реальный текст в сыром HTML,
  без выполнения JS — чтобы Яндекс мог его проиндексировать.
- Личный кабинет и админка (всё, что за логином) не меняются вообще — они и не должны
  индексироваться поисковиками.
- Первая загрузка страницы стала заметно легче за счёт вынесения того, что не нужно
  сразу, в отдельные чанки.
- Cloudflare снова проксирует трафик sever-18.ru.

## Не цели

- Полный переход на серверный фреймворк (Next.js и т.п.) — see design doc обсуждение,
  отклонено: требует другого хостинга (сейчас — статика по SFTP на Beget), большой риск
  сломать рабочий сайт ради задачи такого масштаба не оправдан.
- Изменение текста/контента посадочной страницы (копирайтинг, ключевые слова) — вне
  рамок этой задачи, только техническая видимость уже существующего текста.

## Часть 1 — Cloudflare (ручной шаг, не код)

У пользователя есть доступ к панели Cloudflare. Решение: зайти в Cloudflare → домен
sever-18.ru → вкладка DNS → включить «Proxied» (оранжевое облако) на A/CNAME записи,
указывающей на Beget. Проверка — `curl -I https://sever-18.ru/` должен показать
заголовок `Server: cloudflare` и `CF-RAY`.

## Часть 2 — Уменьшение главного бандла

Подход: найти в основном чанке (`dist/assets/index-*.js`) код, который не нужен на
первом экране гостевой страницы, и вынести его в отдельные динамически подгружаемые
чанки через `React.lazy()` / динамический `import()` — по образцу уже применённого к
Dashboard/AdminPanel паттерна в этом же проекте. Кандидаты на вынос (подтвердить по
факту, что реально тяжёлое): всё, что нужно только после входа/для конкретных действий,
а не для первого показа гостю.

Критерий успеха: `npm run build` — главный чанк заметно меньше 850 КБ; визуально сайт
не меняется; авторизация и обе панели (клиент/админ) продолжают работать как раньше.

## Часть 3 — Пререндер посадочной страницы (для Яндекса)

**Подход:** билд-тайм пререндер только `LandingPage.tsx` в статический HTML,
встраиваемый в `dist/index.html` вместо пустого `<div id="root"></div>`. Компонент не
тянет никаких динамических данных (нет `fetch`/Firestore-запросов, только один
локальный `useState` для показа карты) — значит его можно отрисовать в HTML-строку на
этапе сборки без запущенного бэкенда.

Механика:

1. Собрать `LandingPage` отдельным SSR-бандлом через Vite (`vite build --ssr`), чтобы
   импорты картинок/ассетов резолвились в те же хэшированные URL, что и в клиентском
   билде (через `vite build --ssr` + manifest, стандартный приём Vite для
   пре-рендеринга).
2. Node-скрипт после обычного `vite build`: импортирует этот SSR-бандл, рендерит
   `<LandingPage onEnter={() => {}} />` через `react-dom/server` (`renderToString`) в
   HTML-строку.
3. Тот же скрипт вставляет полученный HTML внутрь `<div id="root">...</div>` в
   `dist/index.html`.
4. На клиенте ничего не меняется: `main.tsx` как и раньше делает
   `createRoot(...).render(<App />)` — реальный React перерисует контейнер поверх
   пререндеренного HTML при загрузке JS. Небольшая асимметрия (React не использует
   `hydrateRoot`, а просто перезаписывает DOM) — это осознанно ок, ошибок гидратации не
   будет, а для пользователя разница незаметна (контент уже виден, просто дальше
   становится интерактивным).
5. Шаг встраивается в `npm run build`, поэтому автоматически попадает в существующий
   GitHub Actions деплой (push в `main` → сборка → SFTP на Beget) — никаких изменений в
   workflow или в способе публикации не требуется.

**Что не входит:** личный кабинет/админка не пререндерятся (не нужно — не для
индексации), никакой серверной части в проде не появляется — итог сборки остаётся
чистой статикой, как сейчас.

**Риски и как проверяем:** если рендер `LandingPage` в Node упадёт (например,
какая-то библиотека обращается к `window` во время рендера, а не только в эффектах) —
это всплывёт сразу при локальном `npm run build`, до деплоя. Проверка успеха: после
сборки `curl https://sever-18.ru/ | grep` находит реальный текст (например, название
услуги) прямо в HTML, не только в `<title>`/`<meta>`.

## Порядок работы

Части независимы, порядок реализации: 3 (пререндер) → 2 (размер бандла) → 1
(Cloudflare — инструкция пользователю в конце). Каждая часть проверяется локальным
`npm run build` + просмотром `dist/index.html` перед тем как считать готовой; деплой на
прод — через обычный `git push` в `main` (существующий CI), после явного подтверждения
пользователя, так как это публикует изменения на живой сайт.
